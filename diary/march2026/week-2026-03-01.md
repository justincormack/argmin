# Week Diary: 1–8 March 2026

130 commits in 8 days. This week took the project from "basic S3 server with
buffered IO" to "streaming erasure-coded storage with multipart uploads,
checksums, and AWS-verified compatibility."


## Saturday 28 February — Hyper migration planning

Short day. Wrote the plan (`plans/http-server-replacement.md`) for replacing
tiny_http with hyper 1.x. The main motivation: tiny_http's synchronous
`respond()` consuming `self` was blocking every path, and we needed async
throughout for streaming. Also disabled chunked encoding in the old server
as a stopgap.


## Sunday 1 March — Hyper migration and 200+ integration tests

**The big migration.** Replaced tiny_http with hyper 1.x async HTTP in a single
commit. The new server uses a fixed-size pool of `HttpFrontend` instances
distributed across requests via `Arc<[Mutex<HttpFrontend>]>`, with configurable
serve-layer timeouts (`ServeConfig`). The async model means we can now stream
request bodies and handle backpressure properly — critical groundwork for
streaming transfers later in the week.

**Then an integration test blitz.** Six major test commits adding 200+ new tests
to the `s3-tests` crate:
- 78 ListObjects V1/V2 tests (pagination, delimiters, prefixes, encoding)
- 12 single and bulk delete tests
- 38 POST Object tests (SigV4 policy validation, conditions, filename substitution)
- 29 conditional request tests (If-Match/None-Match/Modified-Since/Unmodified-Since)
- 14 presigned URL tests (signed payloads, expiry, query parameter handling)
- 28 bucket naming tests (DNS compliance, edge cases, invalid characters)


## Monday 2 March — Anonymous access, CopyObject, versioning, checksums

Another day of filling in test coverage and fixing the bugs the tests found.

**Anonymous access**: 11 anonymous access tests confirming public-read ACL
behavior and access denial for private buckets, plus 3 more testing PUT/DELETE
rejection.

**CopyObject**: 17 integration tests. Found and fixed: copy-to-self must be
rejected (AWS returns 400), and copy-source with versionId wasn't being parsed
correctly.

**Versioning**: 24 versioning tests covering enable/suspend lifecycle, version-
specific get/delete, delete markers, and multi-object delete interactions.

**Checksums**: SHA-256, CRC-32, CRC-32C checksum validation on upload with
storage and round-trip verification. 10 tests. Found that we needed to enforce
algorithm consistency — can't mix algorithms within a request.

**Other**: 42 header validation tests (the Ceph `test_headers` port), 7 atomic
read/write tests, 4 user metadata tests. Added CORS support, tagging support
(fixed 5 correctness issues), PublicAccessBlock enforcement. Implemented 4
previously-ignored conditional request features.


## Tuesday 3 March — Race conditions, new APIs, and multipart planning

**Race condition fixes.** Wrote a plan for serialization and race issues, then
addressed them: centralized object PG locking, hardened the delete path,
added bucket deletion locking.

**New APIs:**
- `ObjectOwnership` with `BucketOwnerEnforced` enforcement
- `GetObjectAttributes` with selective XML response (object parts, checksums)

**Multipart upload infrastructure.** The big architectural work began:
- Schema: new `multipart_uploads`, `multipart_parts` tables per PG
- Types: `MultipartUpload`, `PartRecord`, `MultipartUploadId`
- Trait contracts: 8 new methods on `PgMetadataStore`
- Full `PgStore` implementation for all multipart metadata operations
- Coordinator methods for `CreateMultipartUpload`, `ListMultipartUploads`,
  `UploadPart`
- Data-layout guards on coordinator read/delete paths (inline vs chunked)

Also wrote the fault injection framework for multipart — test-only code that
can simulate failures at any stage of the multi-step upload process.


## Wednesday 4 March — Multipart completion, checksums, and AWS parity

The day multipart uploads went end-to-end.

**Multipart completion pipeline:**
- `CompleteMultipartUpload` coordinator method — assembles parts, validates
  ordering and gaps, computes composite ETag
- `AbortMultipartUpload` and `ListParts` coordinator methods
- Multipart-aware object reads with `shard_pg_id` tracking (each part's shards
  may be on a different PG than the object's metadata PG)
- HTTP routing and dispatch for all multipart operations
- XML rendering and parsing
- End-to-end integration test, then 14 more multipart tests with Ceph parity

**Multipart checksums (full pipeline):**
- Per-part checksum types, schema migration, SQL threading
- CRC-32 and CRC-32C combine primitives (for computing whole-object checksums
  from part checksums)
- Parse and persist checksum algorithm on `CreateMultipartUpload`
- Verify, compute, and store per-part checksums on `UploadPart`
- Validate and compute object-level checksums on `CompleteMultipartUpload`
- Surface checksums in ListParts, HeadObject, GetObject, GetObjectAttributes
- `partNumber` query parameter support for GET/HEAD on multipart objects

**AWS compatibility blitz.** Ran the full test suite against real AWS S3 and
found ~42 failures. Spent the afternoon and evening fixing them:
- Error code alignment (BucketNotEmpty, InvalidArgument, etc.)
- Default to BucketOwnerEnforced for new buckets (AWS changed this in 2023)
- Conditional write/delete header alignment
- If-Modified-Since with future dates per RFC 7232 §3.3
- Timestamp precision and boundary conditions
- BlockPublicAccess and BOE compatibility
- GetObjectAttributes and ChecksumType defaults
- Anonymous request date handling (ignore x-amz-date without Authorization)
- POST policy condition coverage enforcement
- Composite checksum suffix stripping
- DeleteBucket rejection when delete markers or non-current versions remain


## Thursday 5 March — AWS-chunked streaming, UploadPartCopy, delete markers

**aws-chunked streaming upload.** Implemented the `aws-chunked` transfer
encoding that the AWS SDK uses for streaming uploads with content-SHA256
verification. Each chunk has its own signature in the chunk header. Added
SDK integration tests, then hardened with AWS error parity. Found that AWS
rejects `STREAMING-UNSIGNED-PAYLOAD` — we match that behavior.

**UploadPartCopy.** Implemented copy-from-existing-object as a multipart part,
with byte range support. This is how large object copies work in S3 — the
client breaks the copy into multipart parts copied from the source.

**Delete marker fixes.** CopyObject from a delete-marker source must return
`NoSuchKey`, not copy the marker. Requesting a specific delete-marker versionId
returns `400 InvalidRequest`. Both now match AWS behavior.

Replaced remaining ureq calls in ownership and public access block tests with
the AWS SDK for consistency.


## Friday 6 March — Streaming transfers (the big one)

The most architecturally significant day of the week. Implemented streaming
erasure-coded transfers in 5 phases, taking objects from fully-buffered
(256 MB cap) to streamed in fixed-size chunks.

**Phase 1: Storage sessions.** New `WriteSession` API on the storage layer
that accepts data in chunks, erasure-codes each chunk independently, and
writes shards to disk as they arrive. Deduplication via content-addressed
chunk IDs (CRC64 of chunk data). Also decoupled metadata from the EC payload —
metadata is now stored in the object record, not prepended to shard data.

**Phase 2: Coordinator streaming API.** `StreamingWriteSession` wraps the
storage session with PG routing and EC encoding. The coordinator buffers
incoming data to chunk boundaries, then flushes each complete chunk through
EC and storage.

**Phase 3: HTTP integration.** The `PUT /bucket/key` handler now streams the
request body through the coordinator's streaming session instead of buffering
the entire object in memory. This removes the 256 MB object size limit.

**Phase 4: Read-path streaming.** `GET` with chunk-manifest objects reads
chunks on demand, supporting Range requests across chunk boundaries.
CopyObject and DeleteObject updated for chunk-manifest awareness.

**Phase 5: Cleanup hardening.** Scavenger process for orphaned chunks.
Delete and overwrite paths clean up old chunk data. Streaming checksum
security hardening — verify chunk integrity on the read path.


## Saturday 7 March — Streaming UploadPart, bucket metadata sharding, security

**Streaming UploadPart.** Extended the streaming transfer infrastructure to
multipart uploads. Each `UploadPart` now streams through the same chunked
pipeline, with concurrent isolation between parts and abort safety.

**Bucket metadata sharding.** Moved bucket metadata from a single centralized
database into the per-PG stores, sharded by bucket name. This eliminates the
`SqliteBucketDb` single point of contention. `ListBuckets` now fans out across
all PGs and deduplicates. Required aligning fanout semantics for the available
PG set.

**Security review and fixes:**
- Constant-time comparison for all signature verification (HMAC timing attacks)
- `SecretKey` encapsulation — field made private with `new()`/`as_str()` accessors
  so secret material can't leak through Debug/Display
- Bucket enumeration tests confirming we match AWS behavior (404 NoSuchBucket
  for anonymous requests, not 403 — bucket namespace is globally discoverable)
- Enabled 3 previously-ignored tests by fixing POST policy validation and
  presigned URL expires checking
- Bucket deletion serialization with shared lock striping (256 stripes)


## Sunday 8 March — SigV2 removal and cleanup

Removed legacy SigV2 POST Object authentication entirely. The POST Object
endpoint now requires SigV4 form fields only. This eliminated the last
remaining non-constant-time comparison path and simplified the auth crate.
Added the `test-util` crate for per-PID temp directory management across
integration tests.


## Week summary

In 8 days, the project went from a synchronous buffered S3 server to a
streaming async storage system. The major milestones:

1. **Hyper migration** — replaced tiny_http with hyper 1.x, enabling async IO
   throughout the stack
2. **200+ integration tests** — comprehensive coverage of S3 operations,
   verified against real AWS S3
3. **Multipart uploads** — full lifecycle including checksums, UploadPartCopy,
   partNumber queries, and GetObjectAttributes pagination
4. **Streaming transfers** — 5-phase implementation removing the 256 MB object
   size limit. Objects are erasure-coded in fixed-size chunks as data streams
   in. Read path streams chunks on demand with Range support
5. **AWS compatibility** — fixed ~42 test failures against real AWS, achieving
   near-parity on error codes, conditional headers, and edge cases
6. **Bucket metadata sharding** — eliminated centralized bucket database,
   distributing metadata across PGs
7. **Security hardening** — constant-time signatures, SecretKey encapsulation,
   SigV2 removal, bucket deletion locking

The object storage pipeline now looks like: HTTP request → SigV4 auth →
streaming body → chunk buffering → EC encode → PG routing → shard write →
metadata commit. Reads reverse the pipeline, streaming chunks from shards
through EC decode. No object size limit beyond available disk.

Test count: ~1000+ across the workspace, including property-based tests,
fault injection, and integration tests running against both the local server
and real AWS S3.


### Key things that were unexpected

1. **aws-chunked is its own transfer encoding** — the AWS SDK doesn't just
   send `Transfer-Encoding: chunked`. It uses a custom `aws-chunked` encoding
   where each chunk includes a signature. We had to implement a custom decoder.
2. **AWS changed bucket defaults in 2023** — new buckets default to
   `BucketOwnerEnforced` object ownership, which disables ACLs. Our tests
   assumed the old default and broke on AWS.
3. **~42 AWS test failures** — running against real AWS for the first time
   surfaced many behavioral differences that Ceph tests didn't catch:
   timestamp precision, conditional header edge cases, error code names.
4. **Bucket metadata can't stay centralized** — with streaming transfers and
   async IO, the single-threaded SQLite bucket database became a bottleneck.
   Sharding across PGs was necessary sooner than planned.
5. **cargo fmt wars** — the agents kept running `cargo fmt` at unexpected
   times, leading to noisy format-only commits between substantive work.
   Eventually accepted this and moved on.
