# Week Diary: 23–29 March 2026

71 commits in 7 days. This was the authorization and encryption week — SSE-C
encryption, multi-user ownership, ACLs, bucket policy evaluation, and object
lock all went from zero to complete in a single sustained push.


## Monday–Tuesday 23–25 March — EC zero-parity and Content-MD5

Quiet start. Added zero-parity shard configuration support to the `ec` crate,
allowing replication-only layouts (data shards only, no parity). This is
useful for testing and for deployments that want replication without erasure
coding overhead.

Implemented `Content-MD5` request validation for PUT operations. AWS requires
MD5 validation on certain control-plane operations (lifecycle, tagging,
delete-objects, bucket policy); we now validate and reject mismatched MD5
digests on all paths that send `Content-MD5`.

Fixed multipart upload tag persistence — tags specified at
`CreateMultipartUpload` time were not being carried through to the completed
object. Tags are now stored on the upload record and applied atomically at
completion.


## Wednesday–Thursday 26–27 March — SSE-C encryption

Built server-side encryption with customer-provided keys (SSE-C) from design
through to full implementation in a single two-day push.

**Design and core.** Started with the encryption design plan, then
implemented SSE-C for the three main operation types:

- **Multipart uploads** — encrypt each part with the customer key, store
  encrypted segments. The same key must be provided for each UploadPart
  and at CompleteMultipartUpload time.
- **Copy operations** — CopyObject and UploadPartCopy decrypt the source
  with the source key and re-encrypt the destination with the destination
  key, streaming through the segment pipeline.
- **POST Object and presigned URLs** — SSE-C headers are supported in POST
  form fields and validated on presigned request paths.

**Checksum separation.** Separated system metadata (internal checksums,
segment layout) from user-visible metadata. SSE-C checksums are encrypted
alongside the data so they cannot leak plaintext information. This required
restructuring how checksums flow through the storage layer.

**Security hardening:**

- Fixed a nonce reuse vulnerability in SSE-C multipart uploads where
  parts could share encryption nonces. Each part now gets a unique nonce.
- Tightened constant-time comparison boundaries — all secret comparisons
  (keys, signatures, checksums) now use constant-time equality.
- Added bucket-level SSE-C gating — buckets can be configured to require
  or forbid SSE-C encryption.
- Implemented direct TLS support and HTTPS enforcement for SSE-C. Customer
  encryption keys must not travel over plaintext HTTP. The server now
  generates a self-signed certificate for testing and rejects SSE-C
  requests over non-TLS connections.

**Testing and documentation.** Added property tests for storage metadata
serialization, documented SSE-C validator and stable storage configuration,
aligned multipart SSE-C behavior with AWS edge cases. 53 SSE-C integration
tests total.


## Friday 28 March — Ownership, ACLs, and bucket policy

The biggest single day of the project. Implemented the entire authorization
stack in one session.

**Multi-user ownership foundations.** Added typed account identity (`AccountId`,
`CanonicalUserId`) threading through the entire request path. Objects and
multipart uploads now record their owner identity. Ownership controls
(BucketOwnerPreferred, BucketOwnerEnforced, ObjectWriter) are enforced on
write paths. Tenant compatibility cleanup ensured the alt-client test
infrastructure works correctly for cross-account scenarios.

**Expected bucket owner.** Implemented the `x-amz-expected-bucket-owner`
header, which allows clients to guard against operating on the wrong bucket
after a delete/recreate race. Validated against all applicable operations.

**ACL implementation (5 phases):**

1. **Normalization** — parse canned ACL headers, `x-amz-grant-*` headers,
   and XML `AccessControlPolicy` bodies into a canonical internal form.
2. **Bucket ACLs** — `PutBucketAcl` and `GetBucketAcl` with full grant
   round-tripping (canned ACLs, canonical user grants, group grants).
3. **Object ACL grants** — `PutObjectAcl` and `GetObjectAcl` with all
   canned ACL types, canonical user grants per permission.
4. **Multipart ACL integration** — ACLs specified at CreateMultipartUpload
   time carry through to the completed object.
5. **Public access block** — `BlockPublicAcls`, `IgnorePublicAcls`,
   `BlockPublicPolicy`, `RestrictPublicBuckets` all enforced.

**Bucket policy (8 phases, started Friday evening):**

1. **APIs** — `PutBucketPolicy`, `GetBucketPolicy`, `DeleteBucketPolicy`
   with JSON validation and storage.
2. **Classifier** — policy statement matching: Principal, Action, Resource
   pattern matching with wildcard support.
3. **Evaluation** — full IAM-style policy evaluation: explicit deny wins,
   then explicit allow, then implicit deny.
4. **Conditions** — `StringEquals`, `StringNotEquals`, `StringLike`,
   `StringNotLike`, `ArnEquals`, `ArnLike` condition operators on
   request context keys.
5. **Restrictions** — enforce that policies cannot grant broader access
   than the bucket's public access block settings allow.
6. **List access** — bucket policy evaluation for `s3:ListBucket`,
   `s3:ListBucketVersions`, `s3:ListBucketMultipartUploads`.
7. **Extended conditions** — `s3:x-amz-grant-*`, `s3:x-amz-copy-source`,
   `s3:RequestObjectTag/*`, `s3:x-amz-server-side-encryption` condition
   keys.
8. **Policy status** — `GetBucketPolicyStatus` API returning whether a
   bucket policy grants public access.


## Saturday 29 March — Bucket policy completion and object lock

Finished the bucket policy implementation from the previous evening, then
pivoted to object lock.

**Test infrastructure.** Split `s3-local-tests` from `s3-tests` — tests that
require server control (time advancement for lifecycle, bucket naming
validation) now live in their own crate with a local-only test harness.
Fixed AWS versioned conditional delete behavior to match the real service.

**Object lock (full implementation):**

Started with the compatibility plan and AWS-validated test suite (58 tests
ported from AWS validation runs), then built the implementation:

- **Domain model** — `ObjectLockConfiguration`, `RetentionMode` (Governance
  vs Compliance), `RetentionPeriod`, `LegalHold`, `DefaultRetention` types.
- **Storage** — retention mode, retain-until-date, and legal hold persisted
  per object version in the metadata layer.
- **Bucket APIs** — `PutObjectLockConfiguration` and
  `GetObjectLockConfiguration`. Object lock can only be enabled at bucket
  creation time (immutable once set).
- **Object APIs** — `PutObjectRetention`, `GetObjectRetention`,
  `PutObjectLegalHold`, `GetObjectLegalHold`.
- **Write-path enforcement** — PUT and CompleteMultipartUpload apply default
  retention from bucket configuration when no explicit retention is set.
  Retention headers on write requests override defaults.
- **Read-path headers** — GET and HEAD responses include
  `x-amz-object-lock-mode`, `x-amz-object-lock-retain-until-date`, and
  `x-amz-object-lock-legal-hold-status` headers.
- **Delete semantics** — objects under retention or legal hold cannot be
  deleted. Governance mode allows bypass with
  `x-amz-bypass-governance-retention: true` header. Compliance mode is
  absolute — no bypass possible until the retention period expires.
- **Auth surface** — bucket policy evaluation for all object lock actions
  (`s3:PutObjectRetention`, `s3:GetObjectRetention`,
  `s3:PutObjectLegalHold`, `s3:GetObjectLegalHold`,
  `s3:BypassGovernanceRetention`).
