# Week Diary: 16–22 March 2026

56 commits in 7 days. This was performance week — driven by warp benchmarking,
the focus shifted from features to throughput. Every layer of the write and
read paths was profiled and optimized: buffer pooling, zero-copy IO, lock
scope reduction, shard write batching, and a fast path for small objects.


## Monday 16 March — Tracing, read-path optimization, and buffer reuse

Started the day by adding request-level tracing instrumentation so we could
see where time was being spent. Added trace events for multipart offsets,
read layouts, bucket lock hold durations, and response completion timing.

**Segment size tuning.** Increased the internal segment size from 4 MiB to
8 MiB and aligned the default HTTP read chunk size to match, reducing the
number of EC encode/decode rounds per object.

**Read-path optimization.** On healthy paths (no degraded shards), we now
read only the required data shards instead of all shards. Multipart range
reads are bounded to overlapping parts only. Bypassed PG locks on healthy
read paths where lock-free reads are safe. These changes together
significantly reduce read-side IO and lock contention.

**Streaming copies.** `CopyObject` and `UploadPartCopy` were previously
buffering the entire source object or range in memory. Both now stream
through the segment pipeline, removing the copy-size memory ceiling.

**Buffer reuse.** The big allocation work:

- Reduced healthy read path shard allocations (avoid per-read Vec creation)
- Reduced segment copies on write ingress
- Reused whole loaded segments on reads instead of copying
- Avoided copying partial read chunks
- Pooled ingress segment buffers and core read segment buffers
- Reused parity scratch buffers on healthy writes
- Reused degraded read reconstruction scratch buffers
- Avoided copying ingress frame payloads entirely

Also fixed a bug: `CreateBucket` now preserves ownership controls on
idempotent re-creation.


## Tuesday 17 March — Write path profiling and allocation elimination

Closed out the segment buffer reuse plan (a few minor items left not worth
doing). Then shifted focus to the PUT write path.

**Write path lock reduction.** Reduced the streamed PUT metadata lock scope —
the metadata PG lock was being held across the entire segment write, but it
only needs to be held for the metadata commit. Added tracing for PUT handoff
delays to measure the improvement.

**Frontend contention.** Removed the frontend pool mutex that was serializing
request dispatch. Requests now flow through without pool-level contention.

**Shard write batching.** Split shard durability (fsync) from metadata
publish, then batched shard metadata publish for streamed PUTs. Instead of
publishing each shard's metadata individually, shards are batched and
committed together.

**Allocation elimination across the request path:**

- Stored S3 request methods as `http::Method` instead of strings
- Reduced request parsing allocation churn (fewer intermediate Strings)
- Reduced storage path allocation churn (reuse path buffers)
- Kept request headers as `HeaderMap` instead of converting to a custom type
- Moved request headers without cloning
- Stored request URIs without copying path/query components separately
- Reduced auth request string allocations (SigV4 canonicalization)
- Inlined small checksum values (stack allocation instead of heap)
- Inlined storage-side checksum bytes

**warp compatibility fix.** The warp S3 benchmark tool sends requests with
`Content-Encoding: aws-chunked` but without actually using the aws-chunked
transfer encoding. We now strip the `aws-chunked` content-encoding only for
genuine streaming uploads (those with `x-amz-content-sha256` set to a
streaming value), fixing the `malformed trailer` errors warp was hitting.


## Wednesday 18 March — Threat model

Quiet day. Added a threat model document (`guides/threat_model.md`) from
Codex Security. Covers assets, trust boundaries, attack surface analysis,
mitigations, attacker stories, and criticality calibration. Key boundaries
identified: network, authentication, core/storage, FFI (ISA-L), and
configuration. The model notes that TLS and encryption at rest are out of
scope (provided externally), and the server is effectively single-tenant.


## Thursday 19 March — Durable shard write batching

Extended the shard write batching work from Tuesday to cover durable writes.
Previously each shard was individually fsynced; now durable shard writes for
streamed PUTs are batched — multiple shards are written and then fsynced
together, reducing the number of fsync syscalls per segment.


## Saturday 21 March — TCP_NODELAY and response tracing

Short session. Enabled `TCP_NODELAY` on the listening socket so that small
response headers are sent immediately rather than waiting for Nagle's
algorithm. Added tracing for the first response chunk to measure
time-to-first-byte.


## Sunday 22 March — Bucket write reservations and fast paths

The week's optimizations culminated in two architectural changes to reduce
lock contention on the hot write path.

**Bucket write reservation barrier.** Designed and implemented a reservation
system for bucket writes. The problem: `DeleteBucket` needs to wait for all
in-flight writes to complete, but the previous approach held bucket-level
locks during the entire write, serializing all writes to the same bucket.

The new system uses a lightweight reservation counter per bucket. Writers
acquire a reservation (atomic increment) before starting and release it
when done. `DeleteBucket` sets a drain flag that blocks new reservations,
then waits for the counter to reach zero. This allows concurrent writes to
the same bucket while still ensuring safe bucket deletion. Extended the
reservations to cover multipart uploads and deletes as well.

**Single-segment PUT fast path.** Objects that fit in a single segment
(up to 8 MiB after the segment size increase) now take a direct fast path
that bypasses the streaming session machinery. The segment is written and
committed in a single step, avoiding the overhead of session setup,
incremental buffering, and finalization.

**Shared bucket auth fast path.** Added a cached bucket info lookup that
avoids repeated PG queries for the same bucket within a request batch.
Extended this to the hot object auth path — repeated operations on the
same bucket reuse the cached authorization result.

**Tracing improvements.** Added finer-grained HTTP request trace scopes
and buffered trace file writes asynchronously to avoid blocking the
request path on file IO.

Closed out write-path plans with updated status.


## Week summary

This was a focused performance week, triggered by running the warp S3
benchmark tool against the server. The major improvements:

1. **Buffer pooling and zero-copy** — eliminated per-request allocations
   across the entire read and write paths. Segment buffers, parity scratch,
   reconstruction scratch, and ingress frames all reuse pooled memory.

2. **Lock scope reduction** — metadata PG locks no longer held during
   shard writes. Frontend pool mutex removed. Healthy read paths bypass
   PG locks. Bucket write reservations replace coarse bucket locks.

3. **Shard write batching** — both metadata publish and durable fsync
   are now batched across shards, reducing per-segment syscall overhead.

4. **Request parsing** — headers kept as `HeaderMap`, methods as
   `http::Method`, URIs stored without copies, auth canonicalization
   uses fewer allocations. The entire request parsing path is now
   largely allocation-free for the common case.

5. **Fast paths** — single-segment objects (up to 8 MiB) skip streaming
   session overhead. Bucket auth results are cached across operations.

6. **Streaming copies** — `CopyObject` and `UploadPartCopy` stream
   instead of buffering, removing the copy-size memory ceiling.

7. **Observability** — request tracing, lock hold duration tracing,
   response timing, and async trace file writes provide visibility
   into performance without impacting it.

Also added a formal threat model and fixed warp benchmark compatibility.
